Please choose versions by [Semantic Versioning](http://semver.org/).

## Unreleased

- feat: **`/supervisor:manager-loop` and `/supervisor:fleet-loop` take `--interval <N>m`, so a loop can be armed to tick rarely — hourly, say — instead of at a hardcoded cadence.** Both hardcoded their tick in prose (`manager-loop` ~5 min, `fleet-loop` ~15 min) with no way to slow it, and every tick is a full manager turn — measured ~320k cache-read tokens per empty sweep, growing with session age — so the dominant cost lever on an idle topic was unreachable. Default is now **15 min** for both. `fleet-loop` keeps its **15 min floor**; `manager-loop`'s floor is **5 min**, the value it hardcoded before the flag existed, so no previous cadence becomes unreachable. A below-floor value is **clamped up and announced** rather than rejected — a loop that refuses its own interval stops silently, which is the failure this flag exists to reduce. ⚠️ **Two caps bind outside the flag, and are now written down rather than left implicit:** while the session owns a live headless worker the effective interval is `min(<interval>, 900)`, because headless permission parks auto-deny after 15 minutes and a longer tick would resume a worker with a denial it did not earn; and the attention watcher is **not** governed by `--interval` at all — it keeps its own 30-min-bounded arm, so a long tick behind a live doorbell still wakes the manager once per watcher event, which is the intended shape (the watcher is the push channel, the tick is the poll). Both command bodies also record that the value handed to `manager-liveness.py --arm --interval` is the **fallback** basis only: `observed_interval()` prefers the measured median arm-to-arm period once ≥4 arms exist, and the declared value alone once produced five false lapsed-manager pushes in 32 minutes. Runbooks `Manager Session` § Cadence mechanics and its `Fleet Manager Session` twin are updated in lockstep, since they are the single home the commands point at for the tick.

## v0.56.5

- feat: `manager-sweep-reader` gains a topic-level **necessity read** (step 8) — enumerates by each task's `goals:` frontmatter rather than a goal's curated `# Tasks` section (measured 42% coverage), reports the size of the set it inverted, and returns exactly three verdicts: `needed`, `product`, `not needed`. Adds the **product clause** that neither `verify-topic` checks 5–6 nor the two vault-cli anchors carry, so a per-alert output task is reportable as the goal's product instead of silently clean. Carries an explicit `<constraints>` carve-out and a matching `<error_handling>` rule so the reporting path never widens the swept set, and a necessity verdict never changes a bucket, an icon, a count or a section placement. Wires the three callers — `manager-loop`, `manager-status` and `manager-drive` — to pass the topic's member goals, without which step 8 is gated off and never fires.

- fix: **`gate-relay-read` triaged the same closer pane as `question` on one run and `no-gate` on the next.** A finished turn whose `👤 You:` line asks the operator something (`pick —`, `approve:`, `you run:`, `review:`) sits at an idle prompt, and the triage called an idle prompt `no-gate` without saying which reading wins. Measured 2026-09-25 on 0.56.4: panes 1925 and 1942 read `question` at 17:02:58Z and `no-gate` at 17:04:45Z. Plain-text closers are the only class the send leg may relay, so the flip made the relay path unreliable exactly where it applies. An asking closer line is now a plain question, and the rule is checked before `no-gate`. `👤 You: nothing` and `later (on …):` stay `no-gate`.

- fix: **the drive agent can no longer spawn a worker, so it cannot open one without a mode.** `agents/manager-drive.md` declared `mcp__supervisor__spawn_agent` and used it to open rows directly, so the mode classification was skipped and the ledger recorded `mode_source=config` — a defect no prose check can read, because it is defined by a *grant*. The tool is gone from its `tools:`; the agent keeps **every decision** (readiness scoring, the prose and collision holds, the spawn cap, the pre-open disk re-read, the mode classification) and now **returns** `To open` / `To resume` rows for the caller — `commands/manager-loop.md` and `commands/manager-drive.md` — which holds the tool, executes them, verifies against the session registry, and writes `last_auto_resume`. ⚠️ **Routing the opens through a `Skill`-invoked `/supervisor:open` instead was measured and rejected:** that command requires `mcp__supervisor__*` **in the invoking session** (`commands/open.md:400`) and otherwise falls back to wezterm, which the same file states *"cannot produce a headless worker"* (`:404`) — so every open would have come back a **tab**, and a wezterm spawn writes **no ledger row**, which would make the very measurement this change serves pass vacuously. The resume half moved with it for the same reason (`resume=` rides the same tool), and the caller's path A preserves today's **headless** resume where the wezterm route would return a tab. `scripts/check-spawn-mode.py` now lists `commands/manager-drive.md` as a spawn site — the spawn moved out of the agent and into its caller — while keeping `agents/manager-drive.md` listed for the decision half it still owns. ⚠️ **An agent audit then found a second grant of the same class, removed with it:** the file *also* carried `Bash(wezterm cli spawn:*)` — a raw terminal spawn, i.e. the same bypass one surface further out, and one `check-spawn-mode.py` could not see because its grant dimension named only the supervisor tool. Both routes are now enumerated in `GRANT_TOOLS`, with a test proving the second one is caught. `Skill` was dropped from `tools:` too: its only two mentions were negative, and an unused grant is the same capability risk.

## v0.56.4

- fix: **an unroutable attention row was a dead end, and a nameless one wore its spawner's pane title as its identity.** `who-needs-me.py` rendered `unroutable — pane N does not resolve to this session` and stopped: the gate was real, open and answerable, but the row never named how. Measured 2026-09-25 by deliberately parking a headless worker (session `50193c14`, `spawn_agent(interactive=false)`): it inherited its spawner's `WEZTERM_PANE` (pane 0, the Fleet Manager's own tab), so the row was correctly refused a jump by the 2026-09-22 ownership check — and then handed the operator nothing. An unroutable row now also renders the command that answers it, `attention-answer.py answer <STORE item_id> --decision allow|deny`, and `normalize_store_item()` now carries the **store's** `item_id` for it: it had kept only the hook log's `dedup_key`, so a handover built from the row's own `item_id` would have been unresolvable by construction. The same measurement exposed a second hole behind the first — `is_routable()` proves ownership by comparing the pane title to the session's *name*, so a nameless session reached `return True` by design and kept a confident jump to a pane it did not own; a pane provably belonging to another registry session is now refused before that test, which cannot see the case at all. `name_of()` refuses the same borrow, so a nameless row renders its own session id rather than the spawner's name. A routable row is untouched: one jump line, no answer line.

- fix: **the gate relay dispatched once per pane, which costs more than relaying by hand.** `commands/fleet-loop.md` said *"For each entry … read the live question through the `gate-relay-read` agent"*, and `manager-loop.md` dispatched the send leg per pane, so a round with N blocked panes paid N dispatches. Each dispatch carries **~2.2 KB of fixed main-context overhead** before any content — the async launch stub (~1.1 KB) plus the hand-back's harness wrapper (~1 KB). Measured 2026-09-25 on 0.56.0 over 4 real gates: a single-gate read+send relay cost **5,527 B** against the **3,944 B** hand-rolled baseline, while one read covering two panes cost **1,760 B per gate**; overall 3,154 B/gate, a ~20% saving instead of the ≥50% the change was for. Both commands and both agents now require **one read dispatch and one send dispatch per round**, carrying every pane and every answer; the fleet-loop check that confirms a gate is open folds into the same read rather than dispatching per report. No behaviour change inside either agent — both already processed a pane list.

- fix: **both gate-relay agents printed a placeholder timestamp in their header.** The template read `<$(date -u +%FT%TZ)>`, which the agents copied as text and filled with `00:00:00Z` (read leg) and `13:xx:xxZ` (send leg), measured 2026-09-25, although both hold a `Bash(date:*)` grant. The header now says `<timestamp>`, with an explicit instruction to run `date -u +%FT%TZ` this run and paste its output, so a header can be ordered against the pane reads it reports.

## v0.56.3

- fix: **the gate owner filter dropped its own pane→session hop when the gate had already closed, and woke a manager for another manager's pane.** `session_for_pane()` folded the event log's open/close lines and took the newest **open** item, so a gate the feed reported but whose items had all closed by the time the filter read the log resolved to no session — and the filter failed open to `unowned`, emitting exactly the pane it exists to drop. Measured 2026-09-25 in Fleet Manager session `64b4a415`: `emit unowned pane 1908 session=None spawner=None` after 20 consecutive polls dropping the same pane as `peer-manager session=82bf6c3a spawner=56021d2e` — and **all 29** of that pane's items were closed at read time. The hop now resolves pane→session from the newest item **regardless of open state**: whether the gate is still open was already decided upstream by `who-needs-me.py`, which is slow (every session's log, the attention store, transcripts) and can take seconds, so re-deriving it here raced a log that had moved on. ⚠️ Deliberately **not** fixed by failing closed on an unresolved session — that would silently drop real gates, the broken-watcher-looks-quiet failure this module exists to avoid. Two alternative sources were ruled out by measurement rather than assumption: no `.needs.json` carries the affected panes, and the attention store held no item for that producer.

- fix: **a manager now re-arms its attention watcher and acts on a `CLEARED` itself, instead of asking the operator to confirm the clear.** `manager-loop.md` step 6 armed the watcher *once at manager start* and `fleet-loop.md` armed it *at loop start*, but a `Monitor` is bounded at 30 min — so the fleet's only push channel died silently mid-run, and nothing announced that it had. Both now re-arm on expiry/death. And on `CLEARED tab <N>` both confirm with `mcp__supervisor__agent_status` (`awaiting_input: false` = cleared; `true` / `waiting` = still standing; `null` = unregistered, falls back to the pane and is never read as "no gate"), close the corresponding ledger/attention entry on that evidence, and continue — never asking the operator to reply "ok" to a clear the manager can observe itself. ⚠️ Never auto-closes a `message` item awaiting a board answer. Runbooks `Manager Session` § Cadence mechanics and its `Fleet Manager Session` twin are updated in lockstep, and the confirmation mechanism now has a single home — the twin points at it rather than restating the field mapping. ⚠️ That mechanism is also **scoped correctly for the first time**: `mcp__supervisor__agent_status` resolves only workers the calling session spawned (`agents.set()` fires only inside `spawn_agent`), so a peer's worker returns `unknown agent` rather than a status — the fleet manager's ordinary case. For every other session the mechanism takes that session's id from the ledger/attention entry the firing is about (the pane→session hop is `session_for_pane()` in `scripts/gate-owner-filter.py` — ⚠️ `who-needs-me.py --pane-for` is the *opposite* direction, session id in and pane out) and reads the session registry, with the pane as the fallback. The commands also no longer key the trigger on one literal line shape (`CLEARED tab <N>`, which no recommended watcher emits): § Cadence mechanics now owns the shape and says to treat any drop as a clear *candidate*. Both commands now also **grant** `mcp__supervisor__agent_status`: the clause previously prescribed a call neither command's `allowed-tools` permitted.

- fix: **`/supervisor:fleet-verify` check 3 applies a stated stamp rule instead of counting "2+ files".** New `docs/fleet-surface.md` § Session stamps: a session may carry many `claude_session_id` stamps but **at most one on an open task**, task creation never stamps, and a manager never stamps a worker's task. New `scripts/stamp-check.py` applies it deterministically. It fails on a stamp behind 2+ open tasks, lists a *suspect* (a stamp on an open task whose `metrics_sessions` names other workers), exits 2 rather than reporting a missing or empty dir clean, and treats an empty `claude_session_id:` as no stamp. Check 3 had been LLM prose counting files per stamp. Measured 2026-09-25 it flagged 33 stamps: 0 were manager stamps, 30 were an ended session's finished tasks in turn (history that records who did the work), and 3 were a creator's stamp left on an open task. One false "stamp" was `goals:`, read across the newline after three empty fields.
- fix: **`fleet-board.py` ties every `needs-input` row to its own pane.** The `--json` `details` map read the same literal `"waiting on an open gate"` on every row (measured 2026-09-23: 4 of 4), which attributes nothing, so `/supervisor:fleet-verify` check 4 reported UNKNOWN for want of a pane. The pane was already known — every gate record passes `is_live()`, which requires its pane in `wezterm cli list` — and `collect_signals()` discarded it. It now returns it, and each row reads `pane <id> — open <kind> gate` (the `pane <id>` form `who-needs-me.py`'s `_PANE_REF` parses), or a reason naming that session when a gate carries no pane. Only a session's gate records attribute it: its `idle` record is not a gate, and the first cut rendered `open idle, question gates` on the live fleet.
- fix: **`context-usage.py` no longer prints a pane id it has not confirmed.** Every recorded pane id is resolved against `wezterm cli list` before it reaches the table, and a session without a confirmed pane is never offered as a compaction candidate — the state files are written at event time and never rewritten, so a pane id outlived its pane and was printed with the confidence of a live one (measured 2026-09-20: `--compactable` offered pane 109 for a 72h-old session whose pane did not exist, and `get-text` exited 1). Compaction is a no-ask action, so a phantom candidate is a run that reports success and does nothing. A **failed** `wezterm cli list` is its own answer, distinct from an empty one: ids are withheld and the run says so, because an unreadable query cannot prove a pane is gone any more than it can prove one is live. `scripts/tests/test_context_usage.py` is new — the script had no coverage at all.

- feat: **`/supervisor:attention-next` can now answer a `permission`-class item, and delivers it without a Claude-session relay.** `attention-answer.py` refused every non-`message` item, so a parked headless worker's gate could only be settled from the session that spawned it — the arm that exists to answer remotely was the one arm that could not answer a gate. The script now takes an explicit `--decision allow|deny` for a `permission` item, posts it beside `answered_by`, and prints a `DELIVERY: supervisor poll` line **instead of** a `TARGET`. That substitution is the whole change: the wrapping command branches on the line, so a `TARGET` here would have made it `SendMessage` a session — the relay this path exists to remove, and a session cannot release another session's parked gate. **An omitted decision is refused, never defaulted** — neither an implicit allow nor an implicit deny is safe, and that refusal is the guard keeping an irreversible prompt from being settled without an operator-supplied verdict. `ack` items stay refused, since they ask nothing. ⚠️ **Requires attention-controller `v0.6.0`**, which adds the `decision` field this posts; against an older store the answer is accepted and the verdict silently dropped, so this half must not ship ahead of it.

- fix: **`gate-owner-filter.py`'s docstring promised a `--check` flag the script never defined.** The module docstring described its anti-silence guard as *"`--check` reports the drop count"*, but `main()` defines no such flag — the count is printed to stderr on every run, and `--explain` / `--json` are the only output switches that exist. The docstring now names that stderr line, so the guard it advertises is the guard that exists. Caught by the runbook-reconcile pass, which checked each advertised flag against `main()` rather than trusting the docstring. Also drops a duplicate gate-owner-filter entry this merge re-introduced into the unreleased section: it already sits under v0.56.0, and the copy came back because #214 was branched before that release cut and merged after it — the release-plus-open-PR interaction, not a second change.

## v0.56.2

- fix: **a decision carried by a resume now answers the gate, instead of re-asking it.** Measured 2026-09-25: a worker parked on a permission, its spawner was killed, and it was resumed carrying a `deny`. It came back and **re-raised the identical tool call**, parking a second time — the decision had reached the transcript and not the gate. The framing that misleads here is "settle the original promise": that promise died with the spawner's process, so for a spawner-gone worker there is nothing left to settle. The gate worth answering is the one the resumed worker raises in the server that now hosts it, and `server/decision-settle.mjs` decides which carried decision may answer it. Deliberately narrow: a different tool never matches, and a park that named a blocked path requires that path — because applying a decision to a gate it never answered is the replay failure the resume validation already refuses one level up. **Consumed once**, so a decision answers one park and not the worker's whole future, and a carried **`allow` is not auto-applied** — honouring one without the live policy check would make this a laundering path with a new spelling. A carried `deny` only ever withholds, so it always applies.

Resume rows are excluded — they answer to the auto-resume gate.

## v0.56.0

- feat: **the manager's gate relay moves out of the manager's own context.** The Fleet Manager relays operator answers into tab workers by hand — read the pane, batch the question, re-read it, type the answer, read back to verify — and every one of those steps lands in the manager's context. Measured on Fleet Manager session `64b4a415` against a frozen snapshot (md5 `b78ef2dc23fd59fcce6dc5440bc17a80`, 21,545 lines; ⚠️ the live transcript keeps growing, so the hash is what pins the number): **234 pane-call Bash invocations / 418,706 bytes** of tool output, of which **140 calls / 205,113 bytes are relay-attributable** across 52 relayed questions — **3,944 bytes per relayed question**, and **65 of those 140 calls are read-only** (120,464 B), i.e. the read-back is the larger half of the cost. Two sub-agents take it: **`gate-relay-read`** (pane id in, per-pane summary out, `4N+2` lines; holds **no `send-text` grant**) and **`gate-relay-send`** (operator's answer + provenance in, one line out). ⚠️ The split is a **permission boundary, not a capability guarantee** — a `Bash` grant is a prefix glob over a command string, so the read leg is *not permitted* to type into a pane rather than *unable* to; the files say so in those terms and must not be read as stronger. The send leg re-reads the pane immediately before typing — the read that proved the gate open at *surfacing* time does not prove it at *answer* time — repeats a bare `\r` until the composer clears, and reports `not sent` with no pane mutation when the gate cleared meanwhile. **It never drives a selection modal.** `commands/fleet-loop.md` mandated arrow-key navigation into an `Enter to select` pane while `commands/manager-loop.md` and `docs/fleet-surface.md` forbade it, and the latter two were last touched by the *same* commit (`a6b5d0d`) without being reconciled; the operator ruled on 2026-09-25 that a modal pane is a `jump-link.py` handover, and `fleet-loop.md` is corrected to that reading so the three agree. Both commands now **dispatch the agents** instead of carrying the mechanics inline: `commands/fleet-loop.md` § Needs-input and `commands/manager-loop.md` § Path-B relay rules point at `gate-relay-read` / `gate-relay-send`, and the raw `Bash(wezterm cli get-text:*)` / `Bash(wezterm cli send-text:*)` grants are removed from both — the agents hold them, and the commands keep only `list` (liveness) and `spawn` (resume). Verified by `grep -c gate-relay` returning ≥1 in each command and `grep -cE 'wezterm cli (get-text|send-text)'` returning 0 in both.
- feat: **the attention watcher can drop gates a manager does not own, so its model wakes only for its own.** The watcher a manager arms is fleet-wide — `who-needs-me.py` reports every open gate on the machine — and every emitted line costs a full turn, a re-sent session context each. Measured 2026-09-25 on Fleet Manager session `64b4a415`: ~12 wakes in one session for panes owned by other live managers, at a measured median of 345,344 cache-read tokens per turn — roughly 4.1M tokens in a single session, recurring every loop. `scripts/gate-owner-filter.py` resolves ownership through four hops and drops **only** on a live peer manager: pane→session from the event log (`~/.claude/state/attention/*.events.jsonl` — **not** the retired `*.needs.json` store, which carried nothing for the live feed: 0 of 9 feed panes had a record, and **not** the HTTP attention store, which is authoritative for *which* items are open but carries no `pane`), session→spawner from the ledger's `parent_session`, manager-ness by the spawner having **no ledger record of its own** (managers are operator-started, so unlike a worker-spawner they were never themselves spawned; measured 600 records, 15 parents, 11 managers against 4 worker-spawners), and liveness from the session registry. ⚠️ **The keep-set is wide on purpose** — panes this session spawned, panes whose spawner is a worker, panes whose spawner is dead, and unowned panes all emit, because a naive `spawner in live_managers` test includes the watcher's own session and would silence it for exactly the panes it exists to report. An unreadable ledger or registry is **unknown, not empty**, and fails open: reading "the ledger holds 0 records" as "the probe could not be read" is the reasoning error that produced the wrong conclusion at `Manager Session.md:517`. Run live against the fleet: 6 gates, 4 emit, 2 dropped as peer-manager-owned.
- feat: **a resume can now carry the operator's decision into a parked worker.** `resume` took a session id only, so a worker whose spawner died mid-park could only be resumed with its prompt unchanged — which is not an answer. It now accepts `decision: { item_id, behavior, message? }`, validated against the park on that session's ledger record: a bare `allow` with no `item_id` is refused, and so is a decision naming a *different* park, because that is the replay case where one gate's answer is applied to another. The worker is **told** the decision; the tool is not re-run, since the gate was already answered once. Validation and prompt rendering are pure (`server/resume-decision.mjs`), so the rule is testable without a store, a server or a clock. ⚠️ Deliberately **not** in this change: checking that the referenced item was actually *answered* — that needs an attention-store client, which this server does not have, and the ledger record proves a park happened rather than that it was answered.

## v0.55.0

- fix: **an anchored `matchType: "command"` for policy rules, because a Bash `allow` could not be written without opening a bypass.** `ruleMatches` ended in `key.includes(match)` — a substring test — and `overlayRules` places the user overlay *ahead* of the bundled rules, so the natural overlay a reader writes after mining the permission log (`{tool: "Bash", match: "ls ", action: "allow"}`) matched `rm -rf ~/Documents && ls ` and **un-denied a command the bundled `deny rm -rf` had correctly denied**: any allowed substring was a universal bypass, append it to anything. Under the new mode `match` is a **whole-token prefix** of the command — `git status` matches `git status -sb` but not `git push`, and not `git -c alias.x=!cmd status` either, because `-c` stands where `status` must — and four shapes never match at all: a command carrying a shell metacharacter (`;` `&` `|` `` ` `` `<` `>` newline, parens, braces), so composition cannot ride along; a command with a leading `VAR=value` assignment, because the environment picks the program (`PATH=/tmp/evil ls`, `LD_PRELOAD=… ls` and `DYLD_INSERT_LIBRARIES=… ls` each run attacker code under a genuine `ls`); a command holding whitespace the shell does not split on (U+00A0 and other Unicode spaces, `\r`), because a tokenizer that splits where bash does not disagrees with bash about which program runs; and an empty prefix. **Only the prefix is anchored — tokens after it are unconstrained**, so a prefix is safe to allow only when every extension of it is read-only: `ls` is, `sed -n` is not (`sed -n -i`), `find` is not (`-delete`) — and **no `git` prefix is, not even `git status`**: git runs commands named in the repository's own config, the shipped defaults let a worker edit `.git/config` in its cwd, and `git status` was verified to execute a `core.fsmonitor` command, so an allowed git subcommand is prompt-free code execution. It over-refuses deliberately — `grep ';' file` is harmless and still rejected — because the alternative is parsing a shell, and a false refusal costs one escalation while a false allow costs the filesystem. `matchType` is opt-in, so the bundled `deny rm -rf` and every per-spawn policy written before this evaluate exactly as they did; under the anchored mode `match: '*'` means *any single uncompounded command*, not *anything*. This is what `server/policy.json`'s own note — *"the escalated ones are what to promote into rules here"* — needed before it could be done for Bash at all: in `~/.local/state/claude-supervisor/permissions.jsonl` (788 decisions, 2026-09-13 → 2026-09-22) **254 requests escalated (32%)**, 214 of them Bash, and 90 of those 214 (42%) looked read-only on their first word — an upper bound on what rules can absorb, not a figure for it, since every `git` and `sed -n` call lands in that 90 and neither is a safe prefix under the rule above. The first draft of this change skipped leading `VAR=` assignments, matched argv0 alone, and documented `git status` as safe; its own local review found all three before merge.
