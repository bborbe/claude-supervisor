Manager-status slash command — the **read-only, one-shot** twin of `/fleet-status` for a single subject, **goal or topic**. The manager-loop loop is stateful and pings; this is a pure snapshot: "what is this tree doing right now?" Safe to run as often as you like, never sends messages, never arms the loop.

It resolves its subject **exactly as `/manager-loop` does** — same branch detection, same fallback chain, same state files — so the two commands can never disagree about which tree is being reported.

## Arguments

- **`$1` (optional — resolved from the session when omitted):** the **subject** — a goal name matching a page in `24 Goals/`, or a topic name matching a topic page in `23 Topics/`. The branch is detected from whichever page resolves; this command never assumes one.
  - `/manager-status Sentry` → topic branch, reads `23 Topics/Sentry.md`
  - `/manager-status "<Goal Name>"` → goal branch, reads `24 Goals/<Goal>.md`
  - `/manager-status` (bare) → resolve the subject from § Subject resolution below

## Subject resolution — when `$1` is omitted

**The rule has one home:** `${CLAUDE_PLUGIN_ROOT}/docs/subject-resolution.md` — the vault resolution, the four-source chain, the case-insensitive vault test, the "no fallback, ever" clause, the `Subject:` line, and the recording contract (which files, on which resolution). Read it there; **it is not restated here.**

**Only source 3 stays inline**, because it is the one source no agent can be handed — a subagent runs in a fresh context and cannot see the parent conversation:

3. **Conversation** — the most recent `/supervisor:manager-loop`, `/supervisor:manager-status`, `/supervisor:manager-drive` or `/supervisor:manager-verify` argument in this conversation, then the most recent goal/topic page referenced **as a subject** (a wikilink or a read/edited path — not a prose mention).

**Nothing resolves → STOP.** Print `❌ No subject detected. Pass a goal or topic name: /manager-status "<name>"` and do nothing else.

**Print the source.** The first output line is `Subject: <name> (from <explicit|session|name|conversation|last>)`, so a wrong pick is interruptable before the report runs.

**⚠️ Record the resolution — a step to run, not a reference to follow.** Having resolved a subject, run the recording block at `${CLAUDE_PLUGIN_ROOT}/docs/subject-resolution.md` § Recording **now**, before the report. It writes `~/.claude/state/worker-manager/<CLAUDE_CODE_SESSION_ID>.json` — and, on an explicit resolution, `last-<vault>.json` too. ⚠️ **Which files on which resolution is the doc's asymmetry, not this line's — read the block's three cases there before running it**, because running it on an *inferred* subject wrongly promotes that subject into cross-session state for every later tick.

**Then read it back and say which happened.** Present → `✅ Registered: <subject>`. Absent → `⚠️ Not registered — the recording step above did not run`, then run it. **Never report quietly without saying which.** This is the read-time signal; without it the miss stays invisible for the whole life of a healthy session and surfaces only at the moment the session stops and tries to resume itself.

⚠️ **An absent registration is not a role verdict — do not conclude you are a worker.** The tier test keys on that file's presence, but you resolved a subject, so you are a **manager** for it; the file's absence means the step above was skipped, not that the role is wrong. Recognise the tier from evidence you already hold: the subject page you are serving (`24 Goals/<name>.md`, or a topic page carrying `page_type: topic`) and the pane whose title names that subject. **The recovery is the recording step, run now — no operator keystroke and no second session is required.** A session that instead reads the absent file as a role verdict applies the global rule *"Workers Don't Open Sessions"* to itself, stops its own loop and doorbell, and asks the operator what it should be — which is the failure this paragraph exists to prevent. ⚠️ **And if you do find yourself idle and unregistered, emit that tier condition — that you cannot confirm what you are — alongside any "what should this session be" menu**, so a first answer can address the real condition rather than the wrong question.

## Resolution — detect the branch, then read the declared set (same as manager-loop)

**Identical to `/manager-loop` § Resolution step 0.** Probe with the **resolved subject**, not `$1` — under detection `$1` is empty and every probe below would match nothing. Detect the branch, never assume it:

- `find "24 Goals" -maxdepth 1 -iname "$SUBJECT.md"` → **goal branch** below. The folder is the discriminator on this side — **no `page_type: goal` confirmation**; see `${CLAUDE_PLUGIN_ROOT}/docs/subject-resolution.md` § The page test.
- `find "$TOPICS_DIR" -maxdepth 1 -iname "$SUBJECT.md"`, confirm `page_type: topic` **in the frontmatter block** → **topic branch, steps 1–5**.
- **Both match, or neither** → print every candidate path (or `no match`) and **stop**. Never guess between a goal and a topic, and never silently prefer one.

**Goal branch.** Read `24 Goals/<Goal>.md`.

- **Tracked set** = every task whose `goals:` frontmatter names this goal — exact match on the **goal name**, across **all three `goals:` shapes** (list of `[[wikilinks]]`, plain scalar `goals: X`, nested `- - X`); the census and the failure mode live in `/manager-loop` § Resolution — read them there, do not re-derive them here. A wikilink-only match is non-compliant: it renders the tracked set **smaller and complete-looking**, with no error, while every probe passes. This is the declaration; there is no second source.
- **Cross-check against the goal's `# Tasks` list.** A task listed there whose `goals:` does not name the goal, or one whose `goals:` names it but which is absent from `# Tasks`, is a **finding to report** — never silently unioned.
- Print a header line `Goal: <status> · <n>/<m> SC` read from the page, then the same table and the same blocked-by-you jump list the topic branch renders. The `Tracked (N):` line lists the goal's tasks.
- **Closure is not yours.** Report SC status and hand closure to `/vault-cli:complete-goal` — never tick SC yourself, and never flip the goal's status **in order to close it**. ⚠️ **Scoped to closure** — and this command writes nothing at all (§ Subject resolution), so the resolution-time reconcile in `docs/subject-resolution.md` § *Reconcile the subject's status* does not run here. This sentence governs closure, not that write.
- There is no `# Goals` list, no declared-optional set and no `# Status Summary` on a goal. Do not synthesise them; **skip steps 1–5** and go straight to the Procedure.

**Topic branch** — steps 1–5 below.

1. **Resolve the topics folder from config, then find the topic page** — the folder is declared per vault, not hardcoded: `TOPICS_DIR=$(vault-cli config list --output json 2>/dev/null | python3 -c "import json,sys,os;cwd=os.path.realpath(os.getcwd());d=json.load(sys.stdin);print(next((v.get('topics_dir') or '23 Topics' for v in d if os.path.realpath(os.path.expanduser(v['path']))==cwd),'23 Topics'))" 2>/dev/null || echo "23 Topics")`, then `find "$TOPICS_DIR" -maxdepth 1 -iname "$SUBJECT.md"`, confirm `page_type: topic` **in the frontmatter block** (`awk '/^---$/{n++; next} n==1' <page> | grep -q '^page_type: topic'` — unscoped would match the guide's YAML template). Never accept `Topic Writing Guide.md` (it lives in the vault's knowledge-base folder, outside this folder). **`-iname`, not a shell glob** — a plain `ls` glob is case-sensitive under zsh, so a lowercase argument resolves nothing against Title Case filenames (verified 2026-09-12: `*"discord"*.md` → `no matches found`, `*"Discord"*.md` → 5 files), and Resolution step 5's no-fallback rule then reports an existing page as missing.
2. **Read its `## Goals` list** — **An entry in a topic's `## Goals` list may be a goal or a task: a goal admits every task whose `goals:` names it, and a task entry admits that task directly — membership is read from the page and never re-derived.** Tracked set = every declared goal + every task whose `goals:` frontmatter names one of them, across **all three `goals:` shapes**, + every task named directly as an entry (see `/manager-loop` § Resolution for the census and the naive-`\[\[…\]\]` failure mode). **The heading is `## Goals` (a sub-heading under `# Scope`), not `# Goals`** — a literal `^# Goals` match returns nothing, and with no fallback that reads as an empty tracked set rather than as a miss.
3. **Resolve the declared-optional set** — the subset of tracked **task** names the page declares optional. Same rule as `/manager-loop` Resolution step 3 and the Manager Session runbook § Step 4: match **semantically** (wikilink-suffix *and* Non-goals/backticked shapes both occur — keying on the literal `optional (operator, <date>)` misses the second), **never infer from `status`** (`hold`/`backlog` are orthogonal dispositions; the resemblance on Notification System is a coincidence of one page). ⚠️ **Read it at whichever level the page declares it — a goal OR a task.** A goal declared optional contributes **all** of its tasks to the set (the Mantra lane is declared optional as a goal, so all five of its tasks are in it even though no line names three of them), and a task declared optional on its own is in it too. **The set you pass on is always task names** — the frame places tasks, and a required goal owning an optional task renders as a goal row in both boxes, which is correct rather than a defect to collapse. Nothing declared → empty set → one unlabelled box.
4. **Read its `# Status Summary`** — hand-written prose, context only; the snapshot still reads task files directly.
5. **No topic page** — print the missing page name and the fix (`create 23 Topics/<Topic>.md from the topic-page template`), then stop. **Never** fall back to a filename glob, `goals:` scan, theme match, or content grep — a silent fallback is what let scope be re-derived by globbing.

Print the resolution header first, then the tracked set once:

```text
Subject: [<name>](obsidian://open?vault=<V>&file=<relpath>) (from <explicit|session|last|conversation>)
Branch: <goal|topic> (<the page it came from>)
Goal: <status> · <n>/<m> SC          ← goal branch only
Tracked (N): <task> · <task> …
```

⚠️ **Write the set you just printed to a file — through `manager-predispatch.py --write-tracked`, never a shell redirect — and carry its *path* from here on, never the names.**

```bash
python3 ${CLAUDE_PLUGIN_ROOT:-$HOME/.claude/plugins/marketplaces/claude-supervisor}/scripts/manager-predispatch.py --vault "<vault-root>" --subject "<subject>" --write-tracked <<'TRACKED'
<the names you just resolved, one per line>
TRACKED
```

It prints the path it wrote (`~/.claude/state/manager-predispatch/<slug>.tracked.txt`) and refuses an empty stdin rather than clobbering a good set. ⚠️ **The first token is `python3` so the call matches this command's `Bash(python3:*)` grant and raises no prompt** — **`Write` is granted by none of the three commands**, so a bare redirect or heredoc would prompt. The printed `Tracked (N):` line is for the operator; **the file is what the dispatch below carries.** It must be produced by **this run's own scan** — never reconstructed from the roster, a checkpoint, or a previous snapshot. A recalled list is indistinguishable from the right one at the point of use, and a measured one omitted **46%** of the tracked set while every probe passed. ⚠️ **Then compare that set against the gate's own membership before dispatching** — the two are derived by different code from the same declarations, so each reads as self-consistent while they disagree:

```bash
python3 ${CLAUDE_PLUGIN_ROOT:-$HOME/.claude/plugins/marketplaces/claude-supervisor}/scripts/manager-predispatch.py --vault "<vault-root>" --subject "<subject>" --compare-tracked
```

It prints **both counts**, and on a disagreement a **named cause** rather than one undifferentiated line. Exit **0** = identical **or** the known healthy asymmetry; **10** = a divergence **or** the snapshot could not be read; **2** = usage error. ⚠️ **Read the label, not the counts — two causally different cases can share them.** `✅ COMPARE healthy` (caller-only within the page's declared membership, gate-only empty) is what a *correct* tick renders: not a warning, no action. `caller-scan-suspect` (gate-only present while caller-only stayed within the declaration) means **your own scan dropped something**. `caller-overshoot` (caller-only beyond the declaration, gate-only empty) means the scan is too large **or** the gate's snapshot is a refresh behind. `both-sides-moved` exonerates neither side. `caller-format` (the two sets share **no** name at all) is a caller-side format error. ⚠️ **A heuristic, not a proof** — a label names the side to check *first*, never the side already convicted. Full rationale and limits: `scripts/manager-predispatch.py` § `classify_divergence`. ⚠️ **Never collapse the two 10s** — "I could not check" must not read as "they match", and an unreadable *declaration* renders `unclassified` for the same reason. ⚠️ **Report a divergence, never reconcile it here:** the case that motivated the check was one name differing only by a capital `The` against a case-sensitive membership compare, invisible to every other probe because APFS is case-insensitive. Print it; reconciling the sources is a separate task's.

**The subject is always a clickable link.** The operator should be able to open the page the snapshot describes without hunting for it, so the link is part of the header and not an optional extra. Build it per the vault link convention — `obsidian://open?vault=<V>&file=<relpath>`, percent-encoding every character outside `[A-Za-z0-9-_.~]` (space → `%20`, `/` → `%2F`, `→` → `%E2%86%92`) and **dropping the `.md`**. `<V>` is the vault name and `<relpath>` the page path minus the vault root, both read from `vault-cli config list --output json` — never hand-written, because a hand-written path is how a link that looks right opens the wrong page.

The `Subject:` line leads so a mis-resolution is visible before the table renders, and `Branch:` names the page it came from so a wrong branch is legible immediately — the same reason `/manager-loop` prints its branch in the header. Neither line is a verdict; both are facts read from disk.

## Procedure

1. **Pre-dispatch check — decide whether this snapshot is worth a dispatch at all.** Run the gate first. Measured 2026-09-25 on a 26-task tree with 25 done, one snapshot cost **125,423 tokens** for zero new information.

   ```bash
   python3 ${CLAUDE_PLUGIN_ROOT:-$HOME/.claude/plugins/marketplaces/claude-supervisor}/scripts/manager-predispatch.py --vault "<vault-root>" --subject "<subject>" --print
   ```

   - **exit 0 — nothing changed.** The gate has already printed the stored table under its `NO-CHANGE` marker. **Reproduce that output as this snapshot's result and STOP** — dispatch no agent, run no step below. Three things the replay cannot carry, and all are said in the output rather than left to be discovered: the **blocked-by-you jump list** is step 6 and is not persisted; the stored table carries **no jump coordinates** — pane ids are renumbered by a WezTerm restart without moving any digest input, so a replayed link can be dead while nothing reports a change; and the **Session cell is the one the row last had** — since 2026-10-05 the digest collapses `live` <-> `parked`, so a worker that opens a gate with nothing else moving leaves this replay showing a cell that is no longer true (`scripts/manager-predispatch.py` § `digest_of` names the trade-off and its reason; the `NEW GATE` arms in `/manager-loop` step 7 are the surface that does fire, and they are not this one). Say in one line that a fresh run re-resolves all three. Never present a replayed link as live, and never let the missing jump list pass unmentioned — the frontmatter advertises it.
   - **exit 10 — something changed, or the gate could not tell.** Continue to step 2, and persist the fresh snapshot once the table is rendered (step 8).
   - **exit 2 — usage error.** A malformed invocation (missing `--vault`, bad flag), not a verdict. Fix the call; do not read it as "changed".

   ⚠️ **The rule has one home:** `${CLAUDE_PLUGIN_ROOT}/scripts/manager-predispatch.py` — the digest inputs, why liveness is in them, why mtime is not, the fail-open cases, and the reason this store is not the loop's. Read it there; it is **not** restated here. What stays inline is only what this command does with the verdict.

   ⚠️ **This block is shared with `/manager-drive` step 2.** The two copies must keep in sync in: this exit-code branch (0/10/2), the pointer above, and the no-jump-coordinates rule. They legitimately differ in the intro measurement and in the step numbers each exit-10 branch targets. Any other difference is drift — the fail-open clause below is shared and must stay byte-identical.

   ⚠️ **Fail-open is the contract.** A missing state file, an unreadable one, a parse error, an unresolvable subject and a failed write all exit 10 — a gate that reports "no change" when it cannot tell makes a manager blind to its own subject. Never treat a non-zero exit as an error to route around, and never hand-roll a second classifier here: this gate is the only pre-dispatch decision.

   ⚠️ **The snapshot write, declared rather than inherited.** It is the first write in **this Procedure** — the shared recording contract in `${CLAUDE_PLUGIN_ROOT}/docs/subject-resolution.md` § Recording already writes `~/.claude/state/worker-manager/` on an explicit resolution, so this is not the command's first write overall. The snapshot is a **state file under `~/.claude/state/manager-predispatch/`, never vault content**: no note, task, goal or topic page is touched, and the "no vault writes" claim stays true of everything this command reports on. Nothing below is relaxed by it — step 9's *"never fabricate state"* is about what the snapshot *says*, and the snapshot only ever holds a table this command already printed.

2. `ListAgents` — the subject's worker sessions (match by task name), status, age.
   - **Probe liveness for the tracked set — before the delegation, because the reader consumes the verdicts as an input.** For every tracked task carrying an id set, run `${CLAUDE_PLUGIN_ROOT:-$HOME/.claude/plugins/marketplaces/claude-supervisor}/scripts/session-liveness.py --check <id>` once per id across the task's **whole** set — frontmatter `claude_session_id` **and** every `metrics_sessions` id — extracted **by field, never by line start, never by shape** (the `metrics_sessions` entries are indented `    - session_id: …`, so a `^session_id:` match misses them; and a bare-uuid **shape** match sweeps in `task_identifier` — a uuid of exactly the same shape, carried by most task files — which is a **phantom owner**, not a session: the row then reads as owned and silently drops out of `ready-to-start`. A shape match is **non-compliant**, not a shortcut) — and record `<task name> → LIVE | ABSENT | UNKNOWN`, **alive if ANY id returns `LIVE`**. ⚠️ **This is the ownership half of `ready-to-start` and `blocked-upstream`, and the Session cell's `[` / `(` delimiter, and it is yours.** The map must therefore be **complete over every id-carrying tracked row**, not only the ownership-dependent ones: the reader renders the cell from this same verdict (step 7), and a row missing from the map keeps the live-shaped cell by default. The reader may not probe (`agents/manager-sweep-reader.md` `<constraints>` — no `pgrep`/`ps`, no transcript recency), and a subagent inherits your ancestor chain, so its probe would read a false empty for your own session. ⚠️ **`UNKNOWN` (exit 2) is not `ABSENT` (exit 1)** — an unreadable registry cannot prove a session dead — so `UNKNOWN` stays `UNKNOWN` in the map and the reader reports that row's ownership as UNVERIFIED. ⚠️ **Without this input the reader falls back to id *presence* as ownership, which drops every `next` row whose session has died out of the offer — silently, and for the rest of the row's life.** Measured 2026-09-30: **127 of this vault's 557 `phase: todo` rows carry a `claude_session_id`** whose session has ended. ⚠️ **The probe is bounded by the tracked set** — a topic's members, typically under twenty rows — **not** by the vault.
   - **Take the in-flight verdicts the same way, and before the delegation for the same reason.** For every tracked row the `parked-on-unregistered-gate` cell can claim, run the **drive leg's shipped in-flight check, reused verbatim** (`agents/manager-drive.md:100-134` — its own line 132 reads *"Reuse that shipped reading; do not add a fourth definition of 'idle'."*): **the session registry's `status` first** — `shell` ⇒ `in-flight` — **unless the session's newest `Stop` record carries an `⏰ Ends:` slot**; see limb 1's carve-out, `waiting` ⇒ `quiet`, `idle`/`busy` ⇒ no signal, fall through — **then** the `~/.claude/state/attention/<session_id>.tool.json` marker (open inside ~20 min ⇒ in flight; open past it ⇒ do NOT drop — the stuck path fires), **then** the session's transcript mtime against `scripts/who-needs-me.py`'s `LIVE_WINDOW` (5 min) as the last fallback — and record `<task name> → in-flight | quiet`. ⚠️ **The registry limb is the one that carried the answer in both directions** — measured 2026-10-05: six `shell` sessions the transcript limb called `quiet`, and one `waiting` session it called in flight — and it is a **caller** read. ⚠️ **Without this input the reader reports the cell UNVERIFIED, and a worker running long tool calls keeps false-firing as parked.** ⚠️ **Do not substitute the roster's `busy` word** — it is the weaker candidate and is deliberately not the signal, which is why the registry limb reads `shell` and `waiting` only and lets `busy` fall through. Same clause, same wording, in `/manager-loop` — this defect is **mode-dependent**, so a fix in one command says nothing about the other.
   - **Take the feed verdicts the same way, and before the delegation for the same reason.** Read the attention feed's **`Needs you` section** — `python3 ${CLAUDE_PLUGIN_ROOT:-$HOME/.claude/plugins/marketplaces/claude-supervisor}/scripts/who-needs-me.py --section needs-you --all` — map each row's **pane** to its tracked task through the `pane` / `session_id` pair in `~/.claude/state/attention/*.events.jsonl` (the feed prints pane ids only, so the events log is the only join), and record `<task name> → gated | clear | unread`. ⚠️ **`--all` is not optional here.** The section caps at `CAP = 20` rows and prints *"N more — pass --all"*; a tracked task whose gated row falls past the cap is absent from a capped read, and this bullet's own rule — *a section you read and found empty is `clear`* — would then record it `clear`, which is the same false negative input 12 exists to remove, re-entered at the cap boundary. **If a truncated read is passed anyway, the header count exceeds the rows rendered: record `unread` for every task not visibly listed and suppress the fire — never `clear`.** ⚠️ **The join is `scripts/gate-owner-filter.py`'s `session_for_pane` hop, reused verbatim — do not re-derive it.** Pane ids are reused by WezTerm, so **the newest item for that pane wins**, regardless of whether it is still open; a pane with no item at all returns `None`, which the caller treats as unowned rather than as a failure. A feed row that joins to no tracked task, or whose pane resolves to a session that does not own the task, therefore contributes **nothing** — it is not `clear` for that task. ⚠️ **Only `Needs you` is a gate** — the feed renders five sections and the other four are not gates, so a whole-feed row count is not this verdict. ⚠️ **`clear` is not `unread`** — a section you read and found empty is `clear`; a store you could not reach is `unread`, and the reader renders the cell UNVERIFIED rather than reading a failed read as *no gate*. ⚠️ **Without this input the reader cannot take the `genuinely gated` branch at all** — the feed is one half of the `parked-on-unregistered-gate` discriminator, and its absence is why a genuinely-gated row rendered `🔄 progressing` (measured 2026-10-03, tick 115). Same clause, same wording, in `/manager-loop` — this defect is **mode-dependent**, so a fix in one command says nothing about the other.
   - **Take the external-wait verdicts the same way, and before the delegation for the same reason.** For every tracked row with a live owner, read that session's **newest** `event: "Stop"` record from `~/.claude/state/attention/<session_id>.events.jsonl`, take its `⏰ Ends:` slot, and record `<task name> → external | none | unread`. ⚠️ **The log is APPEND-ONLY, so the tie-break is the rule and not a detail.** A session that waited on a machine once and has since been resumed keeps that record **forever**, so a read that takes *any* `⏰ Ends:` record rather than the newest files the row `external` permanently — and because this cell emits **no action line**, the row then silently stops being swept as work, with no signal. Input 12 states the same discipline in the bullet above (*"the newest item for that pane wins"*); this is its equivalent. ⚠️ **The slot must also be NON-EMPTY** — `⏰ Ends:` is emitted by the closer template and a blank value declares nothing, so a substring test alone would file a row as waiting on a machine on the strength of an empty declaration. ⚠️ **`event: "Stop"` is required, and it is the discriminator `is_open_gate()` reads to reach the OPPOSITE conclusion:** a `Stop` record is a rendered closer panel, never a raised gate, so a genuinely-gated worker is never reclassified here and never loses its `⌛ waiting-on-human` cell. ⚠️ **Deliberately not `⏰ Next:`** — the general-purpose forward pointer, which appears on rows waiting on nothing at all: measured 2026-10-04 over **21,349** `Stop` records, `⏰ Ends:` on **4,967** and `⏰ Next:` on 843, and `~/.claude/CLAUDE.md` § Async State Closer scopes `⏰ Ends:` to the 🟡 WAITING panel alone — the one state whose validity rule is *a machine produces the change*. ⚠️ **And not the `👤 You: nothing` line**, which looks like the natural partner and is unusable: a `Stop` record's `detail` holds **one line**, so the two never co-occur, and `👤 You: nothing` alone is also what a plainly **closed** session writes. ⚠️ **`unread` is not `none`** — a store or log you could not read is `unread`, and the reader renders the cell UNVERIFIED rather than reading a failed read as *no wait*. ⚠️ **Without this input the reader cannot take the `waiting-external` cell at all**, and a stopped worker waiting on a machine falls to the in-flight branch and renders `🔄 progressing` (measured 2026-10-03, tick 123). Same clause, same wording, in `/manager-loop` — this defect is **mode-dependent**, so a fix in one command says nothing about the other.
