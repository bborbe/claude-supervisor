## Interval — the tick, its floor and its two caps

`--interval <N>m` sets the tick. Default **15m**; floor **5m** — the value this command hardcoded before the flag existed, so no previous cadence becomes unreachable. A value below the floor is **clamped up and announced** (`⚠️ --interval 2m is below the 5m floor — clamped to 5m`); never rejected, because a loop that refuses its own interval stops silently — the failure this flag exists to reduce.

Parse it out of `$ARGUMENTS` before resolving the subject: `--interval` is orthogonal to the positional `[goal|topic]`, so a session may carry either, both, or neither.

**The tick is one number, used twice.** Pass the clamped seconds to `ScheduleWakeup`'s `delaySeconds`, and the *same* seconds to `manager-liveness.py --arm --interval` (step 3). ⚠️ That record is the **fallback** basis only — `manager-liveness.py` prefers the observed median arm-to-arm period once ≥4 arms exist (`observed_interval()` → `2 * observed + SLACK`). Never present the declared value as the authoritative period: a tick costs real runtime on top of the delay, and the declared value alone once produced five false lapsed-manager pushes in 32 minutes.

⚠️ **Two caps, both binding, neither set by the flag.**

- **Headless park cap — while this session owns a live headless worker, the effective interval is `min(<interval>, 900)`.** A headless permission park auto-denies after 15 minutes, so a longer tick would leave a worker parked past its window and resume it with a denial it did not earn. Announce the cap when it binds. Wrangler auto-policy is the alternative, not the default.
- **The attention watcher is not governed by this flag at all.** `--interval` sets the tick; the watcher `Monitor` stays on its own arm, bounded at 30 min and re-armed on expiry. ⚠️ **At a long interval the watcher still wakes the manager once per watcher event — that is intended, not a leak:** the watcher is the push channel and the tick is the poll, so an hour-long tick behind a live doorbell is exactly the shape this flag exists to make affordable. Never "fix" the mismatch by stretching the watcher. ⚠️ **The arm's rule and its traps live in `65 Runbooks/Manager Session.md` § Cadence mechanics — read them there rather than re-deriving them.** It is scoped **twice**, and neither half is optional: the **section** scope, because the feed's other four sections are not gates, and the **ownership** scope, because the filter's keep-set is wide by design. An unscoped arm wakes the manager on every peer's `Rendered panels` closer — a line the feed itself labels *"a closer line, not a parked gate"*. Measured 2026-10-01 on the Manager Layer arm: **8 wakes in ~55 minutes, 1 actionable**.

## Manager contract — a manager manages, it does not build

The manager **manages; it does not build**. It never performs the topic's *work*: no code edits, no repo/PR/k8s verification, no investigation, no real debugging — not even small ones. (Owner rule, 2026-09-11; boundary restated by the operator 2026-09-18.)

- **The line is work vs management — not read vs write.** Management writes are the manager's own — tasks, task/goal pages, `status`/`phase`, stale stamps, topic-page scope and write-back — via `Edit` / `vault-cli task set`. Code, verification, investigation, debugging and the fix go to a worker. **Delegate the work, not the bookkeeping.**
- ⚠️ **Precedence when a worker already holds the row — this paragraph governs, and it splits by row state.** Three other restatements of the ownership rule give the opposite instruction on a worker-owned row, and until now none of the four named the others: `commands/worker-drive.md` § Peer safety (*"If the task's `claude_session_id` does not name this session, the Progress append is the *only* write permitted — never the title, Success Criteria, Tasks, DoD, or Summary"*) and its § Challenge the acceptance criteria closer (*"Correcting a criterion is a framing change: allowed when `claude_session_id` names this session, otherwise an appended Progress entry plus a `SendMessage` to the owner"*); the vault `CLAUDE.md` § Reconcile On Edit rule (*"Put contradictory evidence in an appended entry plus a `SendMessage` to the owner, never in an edit to their framing"* — whose source is `.claude/claude-md-rules/cr-reconcile-on-task-edit.md`, the file to edit, never the generated `CLAUDE.md`); and `65 Runbooks/Manager Session.md` § Command rationale. **The split, stated here so neither file has to be inferred from the other:** on a row the manager owns, **or** one carrying no live `claude_session_id`, a manager-authored Success Criteria / Tasks / DoD / Summary edit is management and lands directly. On a row a **live worker owns**, the manager **proposes** — an appended `# Progress` entry plus a `SendMessage` to the owner — and the **worker lands the edit on its own anchor**. *Framing* is the axis, not the file: `status` / `phase` / dates / stamps stay the manager's own in both states, which is why clearing a stale `claude_session_id` on another session's task remains a management write.
- ⚠️ **A worker's pane answer and a manager's file answer — the worker reports first, and the operator's answer wins.** A worker answers the operator through `AskUserQuestion` in its own pane while a manager can answer the same questions by editing the file, and from the artifact alone neither party can tell whether the answerer was the operator or the harness — so a manager's edit can land on top of an operator answer with neither side knowing. **The convention (operator decision 2026-10-02 — a convention, deliberately not a mechanism):** a worker that has put a question to the operator **reports the answers back to its manager** — the answers themselves, plus the fact that they were answered — **before** the manager edits the file, and it does so by `SendMessage` rather than by waiting for a reply. **Which actor may override which:** the **operator's answer wins** — a manager that has already edited must not re-edit over an answer the worker reports; it reverts its own edit and re-proposes through the precedence path above. Where two answers genuinely conflict and neither is the operator's, the **row owner's** stands. ⚠️ **This is a convention and nothing enforces it** — a manager that edits before the report arrives can still land an override, which is exactly why the worker reports first rather than waiting. It exists to make the disagreement *visible*, not to make it impossible.
- ⚠️ **This replaces the older "the topic page is the only file the manager may write" rule** (operator override, 2026-09-18). That rule made a one-field status flip a forbidden act and produced a real stall: a task sat `hold` while the manager could only hand the operator a command. Do not reintroduce it as a "fix" — quote this paragraph instead.
- **Never widen past the boundary.** A task-file write is management only while it changes *tracking state* (status, phase, dates, stamps, scope). If it needs the code read, a root cause judged, or a runtime fact verified, it is work — delegate it.
- ⚠️ **Carve-out — a dependency-condition read is management, not work.** The prose-blocker check (clause (2) in `agents/manager-drive.md`, and the pre-spawn bullet below) reads a fact about *whether a dependency the row itself names has shipped* — `gh pr view <n> --json mergedAt,mergeCommit`, `git tag --list <tag>`, or a running artifact's version. That is a **read-only eligibility lookup on the row's own declared condition**, not verification of the topic's work: it judges no code, reproduces no defect, opens no PR and fixes nothing. It is management for the same reason the orphan probe is — without it the manager cannot decide what to start. **Do not read the "no repo/PR/k8s verification" line above as forbidding it**; that line forbids doing the topic's *work*, and a dependency lookup is not work.
- **No worker → spawn one.** Ready-to-start / unowned / orphaned-restart work is started as a new Claude Code session via the Spawn mechanics below — never done in-line by the manager.
- **Task/goal anchored, always.** No work is delegated or spawned without a task (or goal) anchoring it; an unanchored request is not work. Read-only manager business (sweep, table, TTS) needs no anchor; anything else gets a task first (`/vault-cli:create-task "<title>"`).

**The rule has one home:** `${CLAUDE_PLUGIN_ROOT}/docs/subject-resolution.md` — the vault resolution, the four-source chain, the case-insensitive vault test, the "no fallback, ever" clause, the `Subject:` line, and the recording contract (which files, on which resolution). Read it there; **it is not restated here.**

**Only source 3 stays inline**, because it is the one source no agent can be handed — a subagent runs in a fresh context and cannot see the parent conversation:

3. **Conversation** — the most recent `/supervisor:manager-loop`, `/supervisor:manager-status`, `/supervisor:manager-drive` or `/supervisor:manager-verify` argument in this conversation, then the most recent goal/topic page referenced **as a subject** (a wikilink or a read/edited path — not a prose mention).

**Nothing resolves → STOP.** Print `❌ No subject detected. Pass a goal or topic name: /manager-loop "<name>"` and do nothing else.

**Print the source.** The first output line is `Subject: <name> (from <explicit|session|name|conversation|last>)`, so a wrong pick is interruptable before the report runs.

**⚠️ Record the resolution — a step to run, not a reference to follow.** Having resolved a subject, run the recording block at `${CLAUDE_PLUGIN_ROOT}/docs/subject-resolution.md` § Recording **now**, before the sweep. It writes `~/.claude/state/worker-manager/<CLAUDE_CODE_SESSION_ID>.json` — and, on an explicit resolution, `last-<vault>.json` too. ⚠️ **Which files on which resolution is the doc's asymmetry, not this line's — read the block's three cases there before running it**, because running it on an *inferred* subject wrongly promotes that subject into cross-session state for every later tick.

**Then read it back and say which happened.** Present → `✅ Registered: <subject>`. Absent → `⚠️ Not registered — the recording step above did not run`, then run it. **Never arm quietly without saying which.** This is the arm-time signal; without it the miss stays invisible for the whole life of a healthy session and surfaces only at the moment the session stops and tries to resume itself.

⚠️ **An absent registration is not a role verdict — do not conclude you are a worker.** The tier test keys on that file's presence, but you resolved a subject, so you are a **manager** for it; the file's absence means the step above was skipped, not that the role is wrong. Recognise the tier from evidence you already hold: the subject page you are serving (`24 Goals/<name>.md`, or a topic page carrying `page_type: topic`) and the pane whose title names that subject. **The recovery is the recording step, run now — no operator keystroke and no second session is required.** A session that instead reads the absent file as a role verdict applies the global rule *"Workers Don't Open Sessions"* to itself, stops its own loop and doorbell, and asks the operator what it should be — which is the failure this paragraph exists to prevent. ⚠️ **And if you do find yourself idle and unregistered, emit that tier condition — that you cannot confirm what you are — alongside any "what should this session be" menu**, so a first answer can address the real condition rather than the wrong question.

## Resolution — detect the branch, then read the declared set

A name resolves to **either a topic or a goal**; the branch is **detected, never assumed**. Membership is **declared, never re-derived** — never widened by a glob, a theme match or a content grep. Goals and topics close differently (step G).

**The `goals:` declaration has three shapes — match all three.** Membership is read from frontmatter, so the parser must handle every shape the vault actually writes. Census over `25 Tasks/`, 2026-09-18 (826 task files):

| shape | example | count |
|---|---|---|
| list of `[[wikilinks]]` | `goals:` / `    - '[[X]]'` | 385 |
| plain scalar, no brackets | `goals: X` | 2 |
| nested list-of-list, no brackets | `goals:` / `    - - X` | 1 |

**Normalize every shape to the bare goal name, repeating until stable:** strip `[[` `]]`, strip quote marks, strip every leading `- `; re-run all three while anything changed. One fixed-order pass silently drops list or nested entries.

**A wikilink-only extractor (`\[\[([^\]]+)\]\]`) is non-compliant** — it drops the scalar and nested shapes and the set renders silently smaller.

**An empty declaration is not a shape.** `goals: []`, `goals: null` and a bare `goals:` name no goal and are correctly excluded by every parser — do not fold them into the census. 39 of the 42 non-wikilink declarations in `25 Tasks/` are empty, so counting them as misses overstates the damage roughly thirteenfold.

0. **Detect the branch before resolving anything.** Probe with the **resolved subject**, not `$1` — under detection `$1` is empty and every probe below would match nothing.
   - `find "24 Goals" -maxdepth 1 -iname "$SUBJECT.md"` → **goal branch, step G**. The folder is the discriminator on this side — **no `page_type: goal` confirmation**, and the reason is in `${CLAUDE_PLUGIN_ROOT}/docs/subject-resolution.md` § The page test.
   - `find "$TOPICS_DIR" -maxdepth 1 -iname "$SUBJECT.md"`, then confirm `page_type: topic` **in the frontmatter block** → **topic branch, steps 1–4**.
   - **Exact basename, case-insensitive: `-iname "$SUBJECT.md"`** — never a substring glob (topics collide with member goals named after them), never `-name`. Under exact matching a same-folder double match is impossible, so the refusal below applies in both branches.
   - **Both match, or neither** → print every candidate path (or `no match`) and **stop**. Never guess between a goal and a topic, and never silently prefer one. A name that matches neither is not tracked — that is the intended pressure.
   - Print the branch and the page it came from in the header, e.g. `Branch: goal (24 Goals/<Goal>.md)`. A mis-resolved branch must be visible immediately.

   **Step G — goal branch.** Read `24 Goals/<Goal>.md`.
   - **Tracked set** = every task whose `goals:` frontmatter names this goal — exact match on the goal name, **all three shapes** (see the census above; a wikilink-only match is non-compliant). This is the declaration; there is no second source.
   - ⚠️ **The declaration read refreshes every sweep; membership by inference never does.** Three different things — conflating them is the defect this rule exists to prevent:
     - **Declaration read — refresh on every firing.** Re-run the `goals:` scan above and recompute the tracked set. A worker filing follow-up work under this goal mid-run is ordinary fleet behaviour, not a scope change; a set resolved once at manager start makes that work unreachable for the session's entire lifetime, and the table renders complete-looking while omitting it.
     - **Membership by inference — never.** No glob, no theme match, no content grep, on any sweep. A refresh is not a licence to widen by inference; this prohibition is unchanged (see this section's preamble).
     - **Subject and branch detection (step 0's probe) — once, at manager start.** Never re-resolved per wakeup. ⚠️ Step G is nested *inside* item 0, so name the probe rather than "step 0" — a literal reading of "step 0 resolves once" freezes the declaration read along with it, which is the defect this rule exists to prevent.
   - **Print the delta whenever the recomputed set differs from the previous sweep's** — `Tracked: 34 → 38 (+4): <added names>` on growth, `Tracked: 38 → 34 (−4): <removed names>` on shrinkage. `<names>` is the added or removed names, never the whole new set. A set that moves with no line saying so is the same silent-completeness failure in the other direction.
   - **Cross-check against the goal's `# Tasks` list.** A task listed there whose `goals:` does *not* name the goal — or a task whose `goals:` names it but which is absent from `# Tasks` — is a **finding to report**, never silently unioned. The two disagreeing means the declaration drifted, and that is the information.
   - **Closure is not yours.** The goal's `# Success Criteria` are its closure contract and they close **mechanically**. Report SC status and hand closure to `/vault-cli:complete-goal` — never tick SC or flip the goal's status yourself. A goal closing on criteria vs a topic closing on a judged gate is the branch, not a size difference.
   - **Skip steps 1–5** — every one of them is topic-only. There is no topic page, no `## Goals` list, no declared-optional set and no `# Status Summary` on a goal, and **step 5's missing-topic-page stop would fire spuriously on a goal branch**. Do not synthesise them.
   - Everything else — the sweep, buckets, orphan detection, the drive dispatch, spawn mechanics, the status table, TTS, guardrails — is **identical to the topic branch**, because the loop is level-independent.

1. **Resolve the topics folder from config, then find the topic page**: `TOPICS_DIR=$(vault-cli config list --output json 2>/dev/null | python3 -c "import json,sys,os;cwd=os.path.realpath(os.getcwd());d=json.load(sys.stdin);print(next((v.get('topics_dir') or '23 Topics' for v in d if os.path.realpath(os.path.expanduser(v['path']))==cwd),'23 Topics'))" 2>/dev/null || echo "23 Topics")`, then `find "$TOPICS_DIR" -maxdepth 1 -iname "$SUBJECT.md"`, then confirm `page_type: topic` **in the frontmatter block** (`awk '/^---$/{n++; next} n==1' <page> | grep -q '^page_type: topic'`). `-iname`, never a case-sensitive shell glob. Never accept `Topic Writing Guide.md` (no `page_type`; an unscoped grep matches its template). A `24 Goals/` match is a goal → step G.
2. **Read its `## Goals` list** (a sub-heading under `# Scope`, not `# Goals`). An entry may be a goal or a task. Tracked set = every declared goal + every task whose `goals:` names one of them (**all three shapes**) + every task named directly as an entry. Read from the page — never inferred from a task's own `goals:`, its status, or a scan.
3. **Resolve the declared-optional set** — the subset of tracked **task** names the page declares optional. Read it once at manager start. **Unlike the tracked set, it does not refresh mid-run** — the tracked set is *derived* from `goals:` frontmatter and is re-read every sweep (step G), whereas this set is a **written marking on the page**, so Guardrail 5's page-edit half applies to it in full. Full rule: the vault's `Manager Session` runbook § Step 4. Two traps, restated because getting either wrong is silent:
   - ⚠️ **Match semantically, not on a literal string** — optional may be declared as a wikilink in the Current-work / Goals lists or as a backticked name in a **Non-goals** bullet, in varying wording.
   - ⚠️ **Never infer it from `status`.** `hold`/`backlog` are dispositions, `optional` is a declaration, and they are orthogonal. Where a topic's optional tasks happen to be `hold`/`backlog`, a status-keyed shortcut renders that page correctly and mis-groups every other topic.
   - **Member goals render as their own rows, tasks indented beneath.** The optional set is read at whichever level the page declares: a goal (all its tasks optional) or a task. A required goal owning an optional task appears in both sections — not a defect.
   - Nothing declared optional → empty set, and the sweep renders one unlabelled box as before.
4. **Read its `# Status Summary`** — hand-written context, not a source of truth; never add a counter. A change-tick reconciles it from task-file facts (runbook § Write-back on change).
5. **Topic branch only — no topic page** → print the missing page name and the fix (`create 23 Topics/<Topic>.md from the Topic Writing Guide template`), then **stop**. No fallback — no filename glob, `goals:` scan, theme match or content grep.

6. **Confirm no manager already owns this name — before arming anything.** `ListAgents` for `<Topic> Manager` (goal branch: the goal's manager). Hit → print its name and age and **stop**. Miss → re-read the roster **once**; still a miss → proceed and arm. Never probe with `pgrep -f`. Rule: runbook § Step 0.

Print the resolved set at manager start (`Tracked (N): <task> · <task> …`) and **re-print it whenever the declaration read changes it** (step G / step 2) — as a delta line, never silently. Three things stay fixed mid-run, and none of them is the declaration read: membership is **never** widened by a glob, a theme match or a content grep (this section's preamble); the subject and branch **detection** (step 0's probe — not step G's declaration read, which refreshes) resolves **once** at manager start, never per wakeup; and **page *declarations* do not refresh** — the declared-optional set (step 3) is a written marking, not a derived read, so it stays frozen for the run. If the human names a set explicitly, track that set for this run — but say so in the header, since it diverges from the page.

## The open-items ledger — the operator's asks

A manager keeps the **same ledger as the fleet manager**, keyed by its own session and scoped to its subject: it owns the stretch from an instruction being said to a task existing, and from a question being asked to its answer.

Read and write it only through the **`supervisor:open-items` skill** — `/supervisor:open-items <list|add|answer|note|close> …`. The skill is the single home of the kinds, the render rule, the act-every-sweep rule, `answer`-vs-`note`, and `close --evidence`; follow it verbatim, never restate it here. The session id is derived by the script — no `SID` to pass for your own ledger.

## Procedure

1. Read the vault's `Manager Session` runbook (the canonical procedure — follow it verbatim).
2. **Resolve the topic** by reading its topic page (see Resolution above); print the tracked set + the page it came from. No page → report and stop. ⚠️ **Then write the resolved set to a file — through `manager-predispatch.py --write-tracked`, never a shell redirect — and carry its *path* from here on, never the names.**

```bash
python3 ${CLAUDE_PLUGIN_ROOT:-$HOME/.claude/plugins/marketplaces/claude-supervisor}/scripts/manager-predispatch.py --vault "<vault-root>" --subject "<subject>" --write-tracked <<'TRACKED'
<the names you just resolved, one per line>
TRACKED
```

It prints the path it wrote (`~/.claude/state/manager-predispatch/<slug>.tracked.txt`, `slug` = the subject lowercased with non-alphanumerics collapsed to `-`) and refuses an empty stdin rather than clobbering a good set. ⚠️ **The first token is `python3` so the call matches this command's `Bash(python3:*)` grant and raises no prompt** — the same reason the `--save` block below is written that way, and **`Write` is granted by none of the three commands**. A bare redirect or heredoc would prompt on every tick of a 15-minute loop. The file must be produced by **this run's own scan** — never reconstructed from the roster, a checkpoint, or a previous sweep. ⚠️ **A recalled list is indistinguishable from the right one at the point of use, and the cost is measured:** a 128-name list typed from memory omitted **59 of 128 genuinely-tracked tasks (46%)** and swept in **14 belonging to other topics** — and every probe passed while it did so. ⚠️ **Then compare that set against the gate's own membership before anything is dispatched** — the two are derived by different code from the same declarations, so each reads as self-consistent while they disagree:

```bash
python3 ${CLAUDE_PLUGIN_ROOT:-$HOME/.claude/plugins/marketplaces/claude-supervisor}/scripts/manager-predispatch.py --vault "<vault-root>" --subject "<subject>" --compare-tracked
```

It prints **both counts** and, on a disagreement, the symmetric difference under `⚠️ DIVERGENCE:`. Exit **0** = the memberships are identical; **10** = they diverge **or** the snapshot could not be read; **2** = usage error. ⚠️ **Divergence and unreadable are separate lines and must never be collapsed** — "I could not check" reading as "they match" is the defect one level down. ⚠️ **A divergence is reported, never reconciled here:** this command holds no input for which source is right, and the case that motivated the check was one name differing only by a capital `The` against a case-sensitive membership compare — invisible to every other probe, because APFS is case-insensitive so `os.path.exists`, `open()`, Obsidian's link resolver and `ls` all succeed on the capitalised path. Print it in the sweep; reconciling the two sources belongs to a separate task.
