# Attention watchers

When: every tick — arm ONE `Monitor` over the attention feed, and re-arm it whenever it expires or is found dead: `python3 $P/gate-owner-filter.py --feed --self "<this-session-id>" --interval 60` and `python3 $P/answered-watch.py`

  - **Attention watcher:** arm ONE `Monitor` over the attention feed, **scoped by pane ownership** — the filter runs the producer itself and re-reads it every interval, so the arm survives its own first read:

    ```bash
    python3 ${CLAUDE_PLUGIN_ROOT:-$HOME/.claude/plugins/marketplaces/claude-supervisor}/scripts/gate-owner-filter.py \
      --feed --self "<this-session-id>" --interval 60
    ```

    ⚠️ **`60` is a fixed choice, deliberately not derived from the tick's clamped `--interval`** — a slow tick must not slow the push channel. ⚠️ **The `--interval` is what makes this armable at all** — without it the filter reads the feed **once** and exits, so the `Monitor` fires on that read and dies; with it the process stays up and is a **change-detector**, emitting a pane when it **ENTERS** the kept set, never on a re-poll. ⚠️ **A RE-ARM RE-EMITS THE WHOLE STILL-OPEN KEPT SET** — so a fleet holding one open gate pays a full manager turn per re-arm (deliberate: the re-arm is the backstop for a lost wake), which is why the **scope** matters as much as the cadence. ⚠️ **Never wrap the old one-shot pipe in a shell `while true; do … ; sleep N; done`** — that re-emits every kept pane on every poll. ⚠️ **It writes a `LIVENESS  <counts>  new: <n>  change|no change` line to stderr on every poll**, so a correctly quiet arm is not byte-identical to a dead one. It drops a gate whose pane a **live peer manager** owns — whether as the pane's **spawner** or as the **gated session itself** — and keeps everything else (your own panes, a worker-spawned pane, a dead spawner's pane, an unowned pane — the last kept only where that session is not itself a live manager). ⚠️ **The unscoped feed makes a manager pay a full turn per peer gate.** Arm it alongside the tick — and **re-arm it whenever it expires or is found dead, never once at loop start**: a `Monitor` is bounded at 30 min, so an arm-once watcher dies silently mid-loop and the fleet's only push channel goes quiet. ⚠️ **When the pipeline refuses** — `who-needs-me.py` writes `WHO-NEEDS-ME-REFUSED` to stdout, and `gate-owner-filter.py` then exits non-zero without printing a gate count — the manager does NOT arm the Monitor on that output, and renders every feed-dependent cell `unread` while surfacing the refusal text in its tick. ⚠️ **On the self-polling arm printed above, a refusal arrives MID-RUN rather than at arm time** — the filter ends its loop non-zero, the `Monitor` dies, and the **missing `LIVENESS` line** is what tells you; re-arm once the transport answers again. ⚠️ **The tick's `--interval` does not govern this watcher** — it keeps its own arm *and* its own poll period (the filter's `--interval`) — the watcher is the push channel, the tick is the poll. The ownership filter prints each kept pane id **bare**, appending the feed's `⟳replay` mark on any row the feed returned from its event-log fallback — a *candidate to confirm*, never a gate to wake on; the doorbell instead emits `NEW GATE` firings tagged `[<sid8>]`. ⚠️ **This arm emits nothing on a clear**, so a gate **it** raised is resolved only at the next tick — but `manager-loop` step 7 arms a third `Monitor` (`manager-attention-watch.py`, scoped to that manager's tracked set) which **does** emit `CLEARED`, conditional on the session registry. The reconciled rule and the exact line shape have one home: `the Manager Session runbook` § Cadence mechanics. Read `/who-needs-me` on a firing. **Arm the answered-card watcher too — a second, distinct `Monitor`:** `python3 ${CLAUDE_PLUGIN_ROOT:-$HOME/.claude/plugins/marketplaces/claude-supervisor}/scripts/answered-watch.py` emits exactly `ANSWERED <item-id>` when the operator answers a card **this session posted**. It is not a second doorbell — this one fires on a card being *answered* and the ownership filter on a gate being *raised* — so arming both does not double-notify and the "arm ONE" rule above is unaffected. **On an `ANSWERED` line, run `attention-ask.py poll <item-id>` and act on the answer immediately — never wait for the next tick.** Re-arm it on expiry as the feed watcher is re-armed. **A `CLEARED` is not progress until confirmed** — then **close the corresponding ledger/attention entry on that evidence and continue the sweep, never asking the operator to confirm a clear by hand.** ⚠️ Never auto-close a `message` item awaiting a board answer. The confirmation mechanism — which source answers for which worker, and its three-state reading — plus the snippet and traps have one home: `the Manager Session runbook` § Cadence mechanics, and are not restated here.
