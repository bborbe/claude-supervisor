# Covered-subject invariant

When: a covered subject's manager is live

    - ⚠️ **Manager-first is a ROUTING rule, never a trust rule — the fleet still reads the board itself.** Dropping an entry because its manager is live is correct only while that manager is actually raising the ask. A covered subject whose non-terminal rows are **all blocked on the operator** and which has **no open card attributable to it** is a subject the whole stack has gone quiet on, and the manager's own report cannot rule that out: a manager that has stopped posting reports the same `waiting-on-human` rows either way. Measured 2026-10-08: `MDM Bugs` had a live manager, so this bullet raised nothing for it; that manager's under-target branch then suppressed its own card; the operator was told he was being waited on with nothing on the board to answer. **So run the model-free invariant over every covered subject whose manager is live.** ⚠️ **The script is VAULT-side, not plugin-shipped:** `sweep-gate.py` lives in the **active vault's** `.claude/scripts/`, is delivered by that vault's own git, and **this repo does not carry it** — `--invariant` appears nowhere in this tree. The plugin and the vault therefore ship this rule **together** and neither alone is sufficient: this bullet without the vault's script names a flag that resolves to nothing, and the script without this bullet has nothing calling it.

      ```bash
      python3 '<vault>/.claude/scripts/sweep-gate.py' --topic '<subject>' --vault '<vault>' --invariant
      ```

      ⚠️ **Single-quoted, not double** — a subject name is vault-authored model-written content and can carry `"`, a backtick or `$(`, which inside double quotes command-substitute **before** `python3` sees the argument. This is the repo's own rule for exactly this class of value (`commands/goal-loop.md`'s row-claim bullet); the other interpolations in this file are double-quoted because they are not vault-authored.

    It prints a card payload on stdout **exactly** when that subject is operator-blocked with zero cards of its own, and nothing otherwise — an empty stdout is the ordinary case, not a failure. ⚠️ **So the EXIT CODE, not stdout, is what separates a quiet subject from a broken install.** `0` → post if there is a payload; `3` → another layer already holds it, drop it; **any other exit — including `python3`'s own `2` when the script is absent at a typo'd or not-yet-landed `<vault>` path — means the vault-side script is unavailable: report it ONCE PER ROUND in one line — not once per subject, since this runs per subject — and post nothing.** A missing script and a genuinely quiet subject both produce empty stdout, and only the exit code tells them apart; without this arm a broken install degrades to silence, which is the exact failure this bullet exists to remove.

    ⚠️ **Claim the subject before posting, through the SAME `supervisor:asked-ledger` skill the `Claim before asking` bullet BELOW uses — and name the key form: `--row '<the subject the invariant named>'`, single-quoted.** That skill requires **exactly one** of `--session <blocked-session-id>` or `--row '<row-key>'`, and a subject is neither: this card's subject is a topic slug with **no blocked session** behind it, so `--session` has nothing it could be given and `--row` is the only slot that carries it — the same reason `commands/goal-loop.md`'s under-target branch claims its own session-less candidates on `--row`. Naming the form is what makes the claim checkable at the point of use: a reader who cannot name the flag cannot run the claim, and the exit code below is the only thing that reads the guarantee. **sweep-gate exit 0 WITH A PRINTED PAYLOAD, THEN claim exit 0 → post** through `attention-ask.py post --producer-kind manager --dedup-key '<the key the script printed>' --payload '<the card's payload>' --context '<the card's context>' --option '<option 1>' --option '<option 2>' --recommend '<the card's recommendation>'` — **the script prints every one of those fields, so this path assembles none of them**; **claim exit 3 → another layer already holds it, so drop it and say so in one line**, exactly as that bullet prescribes. ⚠️ **The payload condition is not decoration.** Exit 0 with empty stdout means the subject is **not** operator-blocked — the ordinary case — and claiming it would hold a claim for the whole prune window with no card to answer for it, refusing every other asker on that subject. The row-claim bullet in `commands/goal-loop.md` names the rule: *"Take the claims only once this branch is known to run."* ⚠️ **The two 0/3 pairs above are DIFFERENT contracts** — the script's is the paragraph before this one, the claim's is this sentence — and a reader who takes them for one posts after a claim that returned 3, which is the collision this bullet exists to prevent. ⚠️ **The post's five values are SINGLE-quoted, like the invocation above** — they are script stdout and card content assembled from that same vault-authored source; a value carrying a literal `'` is written `'\''`, the fourth hazard `skills/asked-ledger/SKILL.md` names. Without this the covered-subject path *is* the collision that bullet exists to prevent: two askers can hold the same subject and neither sees the other's batch. ⚠️ **Say which askers the key actually joins, because the answer is narrower than that sentence sounds.** The claim refuses a second claimer on the **same key**, so it closes fleet-round against fleet-round, and any other layer that claims this subject on `--row`; it is silent against a claimer on a **different** key. The live-manager half is closed by the invariant's own conjunction rather than by this claim — the card fires only when the subject holds **zero** open cards of its own, so a manager that has already posted makes this path silent — and `commands/goal-loop.md`'s under-target branch keys on the **row**, not on the subject, so the two keys do not meet. Name the key form when you claim, so the next reader can tell which half they are relying on. **The dedup key is the one the script printed** — never hand-derived, and its format is deliberately **not** written down here; `attention-ask.py post` requires it, and the store's open-scoped suppression is what stops a second round re-asking. A subject the invariant is silent on needs no card; a subject it names is one whose manager has gone quiet, and the fleet is the layer that must not go quiet with it. The invariant's **dedup key** has one home — that script — and its format is produced there for exactly that reason; the predicate and the attribution are named here only as far as this path needs them, and that script remains their authority.
