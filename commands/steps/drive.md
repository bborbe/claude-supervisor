## Step 3b — Drive: dispatch the drive leg

Reap is the drive leg's: **reap runs before drive**, which is why the dispatch sits after the sweep and never before it.

**Re-read the digest's `BLOCKED` rows — this session runs the probe, the agent applies it.**
`python3 $P/who-needs-me.py --section needs-you --section board-missing --all`, once, here: this is the drive leg, so the read lands after the sweep wrote the digest and before anything renders. Stamp `date -u` at the moment it returns, and pass **the confirmed pane ids plus that stamp** in the dispatch prompt, labelled `blocked-reread:`. ⚠️ **The agent holds no `python3`** — its `allowed-tools` carries no `Bash(python3:*)` — so a rule telling *it* to run this would never execute; the split is the one the rest of this leg already uses. ⚠️ **A probe that errors is passed as an error, never as an empty set** — the agent then keeps every row and prints `re-read failed: <why> — rows unverified`, because an unreadable store is not a clearance. The rule, its drop scope (a `CLOSERS`-sourced row is never dropped by this probe) and its two directions live in `docs/blocked-row-reread.md`; none of it is restated here.

`Task(subagent_type: "supervisor:fleet-drive", prompt: <this round's sweep hand-back verbatim + the payload= path it named + this session's name and id + vault path + round timestamp + the `blocked-reread:` pane ids and stamp + "dry-run: false">)`
⚠️ **The digest render does not ride this prompt.** The agent reads it from the `payload=` path you pass — the same file Steps 3, 11 and 14 read. Forward that path verbatim; a prompt that drops it leaves the drive leg with no rows.
The plugin prefix is required — a bare `fleet-drive` resolves to a personal `~/.claude/agents/` copy. The agent loads the ledger, suppresses re-nudges, verifies each `parked` session's blocker live, reaps the finished (its step 1b), persists the ledger, and writes the drafted `REAPS`, `NUDGES` and grouped escalation batch to its payload. It owns those rules — read them in `agents/fleet-drive.md`; this command does not restate them.

⚠️ **The agent never sends.** It has no cross-session address, so the sends stay here — the same split `commands/fleet-drive.md` uses.
**Send, from this session.** Every `REAPS` line first, then every `NUDGES` line — reap before drive. For each line, re-check the target's roster status first: moved to `busy`/`shell` since Step 0 → skip and report the skip (never preempt a busy peer); otherwise `SendMessage(to: <exact roster name>, message: <text>)`. Report any failed send — the ledger already counts it as nudged.
**Print** the agent's payload verbatim — read it at the `payload=` path its hand-back named, then print the **`UNVERIFIABLE` block first** (always, including its `(none)` form), then escalation groups, the `Waiting on your keystroke` list and the ledger line — followed by `Sent: <n>` with one line per recipient and `Skipped: <n>` with reasons.
⚠️ **Run the artifact gate EVERY round, after printing the block** — `python3 $P/check-drive-unverifiable-paste.py --digest <the digest path this round swept> --drive <the payload= path>`. It must not be conditional on the payload lacking the section: a payload that carries the block while the `.digest` lost its mirror is exactly the round the gate exists to catch. Report a FAIL in the round's output — a round that lost the block and a round where nothing crossed the threshold must never read the same. The block is mirrored into the `.digest` by `drive-unverifiable.py handle --digest` (the agent's step 6b), so both artifacts answer "was anything unverifiable"; the check verifies both. ⚠️ **A 6b refusal is the exception** — the script writes no block when it exits 2, so report that round as `unverifiable: refused` (below) and do not read the check's FAIL as a lost paste. ⚠️ **A 6b `mirror failed` (exit 3) is the other exception** — the block rendered and printed but the digest could not be written, so say `unverifiable: mirror failed — <its stderr>`; the `.drive` still carries the block and only the `.digest` half is lost.
**Post one attention card per `UNVERIFIABLE ESCALATIONS` row** — `python3 $P/attention-ask.py post --producer-kind manager --dedup-key unverifiable-<sid8> --payload "<that row's card: text>" --risk routine`. The drive leg drafts these and never posts them (it holds no store client); the session that owns the board does. A dedup key per session means a session that stays unreadable does not stack a new card every round. ⚠️ **Do not post a card for an `observation` row** — those render in the `UNVERIFIABLE` block and in neither paste block, because a session with no pane is gone rather than silent; a card about it would name something nobody can act on. ⚠️ **Do not post a card for a `blocked` row here** — those reach the operator through `Waiting on your keystroke`, and this card is only for a session whose own state could not be read.
⚠️ **A refused `drive-unverifiable.py` (exit 2) is reported, never read as a quiet round.** The agent's step 6b prints no `UNVERIFIABLE` block on a refusal, which is byte-identical to a round where nothing crossed the threshold; say `unverifiable: refused — <its stderr>` in the round's output instead. Its ledger read is the same one step 3 already reports on, so a corrupt ledger surfaces there first — this line covers the entries-payload refusal, which nothing else sees.
⚠️ **The `UNVERIFIABLE HELD BACK` block is printed too, verbatim, whenever it appears.** The script acts on at most the per-round cap it applies and names the rest rather than dropping them; a backlog that printed nothing would be indistinguishable from a threshold that stopped firing. Do not act on a held row's behalf — its streak keeps advancing and it becomes eligible on a later round. ⚠️ **The cap's value lives in `scripts/drive-unverifiable.py` (`MAX_ACTIONS`) and is deliberately not restated here** — a number in prose goes stale the moment it is tuned.
**Print the share** — **truncate `/tmp/drive-sent.txt` first** (`: > /tmp/drive-sent.txt`), then write the session ids this round actually sent to or posted a card for (every `Sent:` recipient and every `UNVERIFIABLE ESCALATIONS` card) to it, one per line — an `observation` row is neither, so it never belongs in this file, then run `python3 $P/drive-share.py share --round <round ts> --digest <the digest path this round swept> --entries /tmp/drive-round.json --sent /tmp/drive-sent.txt` and print its `SHARE` block and its last line verbatim. ⚠️ **The truncate is load-bearing.** The path is fixed, so a round that sends nothing and does not truncate leaves the previous round's ids in place and `--sent` then credits sends that never happened this round — the exact overstatement this flag exists to remove. ⚠️ **`--sent` is not optional in practice** — without it a DRAFTED action counts as taken, so the numerator credits messages that never left; the block prints `send state unknown` when it is missing, which is a defect to fix rather than a rendering choice. ⚠️ **Never computed by hand and never omitted:** it is the round's one measure of whether any of this changed anything, and `share: 0/0 (n/a)` on a round that detected nothing is the honest reading, not a blank. A non-zero exit prints `share: refused — <its stderr>`; a refused read and a quiet round must never render the same.
**Open the round's incidents** — `python3 $P/incident-ledger.py stall --round-id "<round ts>"`, then the same with `escalate`. `stall` opens one incident per session whose drive streak has reached `SUPERVISOR_INCIDENT_STALL_ROUNDS` (it reads the streak `drive-unverifiable.py` already keeps — never recount it here); `escalate` posts a board card for any incident past its deadline and stamps `escalated_by: round:<round ts>`. ⚠️ **`--round-id` on both** — it is what distinguishes a round's escalation from a hand-run's, and the negative-control check reads exactly that stamp. An exit 2 wrote nothing: report it, do not retry by hand.
**No usable report** — errored, came back empty, or is not the report — → say so in the round's output. Nothing was reaped and nothing was sent this round; never fall back to a hand-rolled classification — every verdict would be UNKNOWN, and an empty fleet and a dead source must never render the same.
**The `Waiting on your keystroke` list still prints on that round.** The `Waiting on your keystroke` list is the round's operator to-do list — print it as it arrives, never re-assembled by hand; the drive agent builds it and its rules live in `agents/fleet-drive.md`. **Lead it with the round's ONE board line** — `python3 ${CLAUDE_PLUGIN_ROOT:-$HOME/.claude/plugins/marketplaces/claude-supervisor}/scripts/attention-board.py` → `Board: 3 open — http://127.0.0.1:18080`. ⚠️ **Exit 3 means the script printed `board unavailable`** — the store is unreachable, so print that line in place of the board line and say the board was unavailable. Build the list from the attention feed: `python3 $P/who-needs-me.py --all`, one row per entry, oldest wait first and **numbered**. Resolve each row's link with `python3 $P/jump-link.py <pane>` — the same two-step the sweep uses (`--pane-for <sid8>`, then `jump-link.py`) — and print `no pane — <reason>` verbatim for a row whose pane does not resolve. ⚠️ **Keep a row's link only when the row is a class D/E gate or a selection modal** — a board button cannot release those — and answer every other row on the board. **Exclude rows whose session name marks them a fixture or a self-test** (a name containing `FIXTURE` or `SELF-TEST`, case-insensitive). ⚠️ **This is the one path in this command that renders a link itself**, and it does not soften the keep-in-sync rule below — that rule governs the *drive leg's* rows, which arrive already rendered. Never emit a bare `/supervisor:jump <N>` here either, and never a hand-built URL.
**Every `ESCALATION` row carries its jump link — and this session renders none of them.** The drive agent hands each row its already-rendered link, produced by `fleet-sweep-reader` from the pane it resolved. Print the rows as they arrive. **Run no per-row pane read here**: no `jump-link.py`, no `who-needs-me.py --pane-for`. A row carrying `no pane — <reason>` prints that string verbatim; a row the digest could not resolve for is the sweep's to report, not this session's to look up. Never emit a bare `/supervisor:jump <N>` and never a hand-built URL. **Keep-in-sync block** — shared with the round command's step 5, `commands/fleet-drive.md` router row 5 (the drive leg); change one, change the other.
So the manager **informs**, which is read-only context and needs no approval — the `REAPS` lines in the agent's payload **are** that message:

1. The agent verifies the three disk facts above before drafting one.
2. Send it verbatim, from this session; it states the disk state, names that the operator has **not** answered, and leaves the decision with the session.
3. Report the finished rows in Step 5's grouped report as **self-closeable** — one line for all N, never N approvals.

Where a manager owns the session, it reaps its own — this layer defers.
