# Under-target

When: live workers below target **and** no ready row **and** the ask not declined

- under-target → **propose the next most important rows, ranked — never a bulk set.** This is the branch that fires when a tick has **nothing ready to start**: the measured failure was five managers reporting *"nothing approved and ready to start"* and stopping while 36 rows waited for approval, because no manager treated an under-capacity fleet as a reason to propose work. **Trigger — both halves, read this tick:** (a) live workers **below** the fleet-wide worker target (`docs/fleet-surface.md` § Spawn a worker item 5; count via `scripts/worker-sessions.py --count`, never `live-workers.py` or `--list | wc -l`), and (b) this tick produced **no ready-to-start row**. ⚠️ **And a third input gates the post — a declined ask.** A tick whose candidate set the operator has already declined posts **no card**; the declined-ask state is read before the post, never assumed, and never inferred from the `waiting-approval` batch's own skip history (see the suppression sub-bullet below). Then post **ONE** card through the **same mechanism and dedup-key discipline as the `waiting-approval` bullet above** — `attention-ask.py post-batch`, never a second posting path — naming the rows **`agents/manager-drive.md` clause (7) ranks**, in that clause's order and within its cap. ⚠️ **"Same mechanism and dedup-key discipline" names HOW to post, never WHICH card this is.** This is the **ranked** card, and it is a different ask from the `waiting-approval` batch above — that one carries the topic's waiting set, this one carries the next few within clause (7)'s cap. ⚠️ **A skip history on the batch is therefore not a skip history on this card**, and reading the two as one form is how a manager suppresses a card the operator has asked for: measured 2026-10-02, four `skip` answers to the batch were read as a decision against this card and it went unposted until the operator said explicitly that it was wanted and that the skips had been about the bulk form.
  - ⚠️ **The ranking and its cap have ONE home — clause (7).** Never restate its three ranks or its count here: a second copy is exactly the counter a `grep` cannot tell from a real one, which is the defect this change exists to remove. This bullet owns the *trigger* (capacity) and the *ask* (a card); it never owns the ordering.
  - ⚠️ **Ranked, never bulk — operator ruling 2026-10-01, verbatim:** *"We have topics with 100 tasks and approving and starting all of them is not a good idea. So we should always look at the next important tasks we should approve and open."* **Goal-level bulk approval is rejected.** A topic with 100 tasks gets its next few, not its 100.
  - ⚠️ **ONE card per round**, never one card per row — the same rule the `waiting-approval` bullet above carries, for the same reason. When both branches fire on one tick they produce **one** card between them, not two.
  - ⚠️ **Rows must be disjoint from every other manager's card this round.** Claim each candidate through the `supervisor:asked-ledger` skill (`/supervisor:asked-ledger claim --row '<the row>' …`) before it goes on the card — keyed on the **row**, where the blocked-set batch keys on the blocked session, because these candidates are `phase: todo` rows that carry no blocked session at all; the claim protocol's rules live in that skill and are not restated here — including its quoting rule, which is why the key is **single**-quoted above: a row key is a task name, so it can carry `"`, a backtick or `$(`. ⚠️ **Take the claims only once this branch is known to run** — the `at target` gate below short-circuits it, and a claim taken before that check is held with no card to answer for it. ⚠️ **And release them on every path that ends the round without a card** — the suppressed tick (`… suppress`, whose predicate has **ONE home — the declined-ask bullet below** — and is never restated here; ⚠️ **it is the INVERSE of *"rows carrying a non-`✅ Ready for approval` verdict"***, which describes the **re-post** case and is satisfied by a blank verdict) resolves every row it claimed, because it posts nothing and so never reaches the `ANSWERED:` bullet below; an unresolved row claim keeps refusing every other manager (exit 3) for the whole prune window. A row another manager already holds is **dropped from this card and the drop is printed**; never silently substituted.
  - ⚠️ **At or above the target this branch does not run at all** — no card, no open. Print one line saying so (`at target: no card`) so a suppressed tick is distinguishable from a tick that simply found nothing; a silent tick and a suppressed one must never render the same.
  - ⚠️ **A declined ask is not re-posted — the decline is an input this branch reads, not a silence it assumes.** The store cannot be the discovery path: `attention-ask.py` exposes only `post` / `post-batch` / `poll <item-id>` (no list-answered-items read, and the list endpoint filters to open items), and this branch's dedup key names the round's row set — so a declined card is a fresh key the branch cannot look up. The state is therefore the branch's own. ⚠️ **The state file, its dedup key, the per-row startability snapshot, the re-post verdict and the suppression line are produced by ONE script — `scripts/under-target-state.py` — and this branch calls it rather than hand-rolling any of them.** It owns the file's shape, the `--dedup-key` derivation (over the row set's *membership*, so a re-ranking that names the same rows does not move the key), the snapshot's per-row bits and the line it emits. **`… write` on post, `… compare` before posting** (and `… read` when the suppression line needs the item id); a tick that posts without writing leaves the next tick nothing to compare against and this rule inert. ⚠️ **Measured 2026-10-02, and it is the reason this is a producer rather than a better description:** four subjects carried four different hand-rolled derivations — **two folding a timestamp into the key**, so a re-post of an *unchanged* set was a *different* key, the store's open-scoped suppression never matched, and the operator was asked the same question twice. ⚠️ **And a hand-rolled line is bypassed, not corrected** — no script call, no line. On `ANSWERED: skip`, compare this tick's clause-(7) candidate set against the declined set — **a candidate set that is a subset of the declined set and whose rows can start now exactly as they could when the operator declined posts no card** and prints the line `… suppress` emits — which carries the item id, the withheld row names, the capacity line and the ranked rows. ⚠️ **The test is on the ASK, never on the row names alone.** Membership is the wrong unit: the operator declined *work they could start*, so a set whose rows are all unstartable is **not the same ask** however identical its membership. ⚠️ **"Can start" is not a new derivation written here — and it is NOT the `ready-to-start` bucket, because this branch's candidate set never enters it.** Clause (7) ranks the **`phase: todo`** rows, which render `⌛ waiting-approval`, never `ready-to-start` — `agents/manager-drive.md`'s own words: a `todo` row is *"never a dispatch candidate for opening, whatever the caller's bucket said"*. **The surface that actually renders THIS population is the audit verdict each ranked row carries** — `✅ Ready for approval` against `🗑 Stale` / `🔧 Repairable` / `❓ Needs you` (`agents/manager-drive.md` clause (1)) — plus the two exclusions owned elsewhere: the **hold** store (`~/.claude/state/session-holds.json`, rendered `⏸️ HELD`) and the row's own **`defer_date`**. ⚠️ **The audit's 9/10 readiness bar is not the verdict** — the bar is a pre-spawn precondition, while the verdict is what the row renders; only the verdict is readable here. **So a ranked row is UNSTARTABLE when its audit verdict came back PRESENT and is anything other than `✅ Ready for approval`, or the row is held, or it is deferred — nothing else may be assumed unstartable, and `under-target-state.py` owns nothing here beyond the row set and its bits.** ⚠️ **A verdict that did NOT come back is neither startable nor unstartable — it is UNKNOWN, and unknown re-posts.** *"A verdict other than `✅ Ready for approval`"* is satisfied by a **blank** verdict, so reading that phrase as the unstartable predicate lets a degraded audit read withhold the card — the same silence this branch exists to break, reached through a hole in the predicate instead of through the subset rule. The three tokens are the script's (`--startable` / `--unstartable` / `--unknown`), and `compare` refuses a row it is not given one for, so a caller can leave a row neither silently unknown nor silently unstartable. Measured 2026-10-08: five rows sat in the `ready-to-start` bucket with none startable (the operator's own recorded hold, the audit's hard gate, one rendering `⏸️ HELD`), the branch suppressed on membership, and the subject reported itself operator-blocked for hours with nothing on the board to answer — the exact silence the vault-side `sweep-gate.py` invariant exists to break. **A candidate set that is not a subset of the declined one re-posts, and so does one carrying a row that was UNSTARTABLE in the declined snapshot and can start now** — and so does one carrying a row whose startability **cannot be read** this tick, or a row that **cannot start** this tick at all, since a set that can no longer start is not the ask the operator declined. ⚠️ **Do not paraphrase these four arms — `… compare` is their one derivation and prints which fired.** The `--context` names what it printed, never a hand-derived summary of them: a summary that lists three of four arms reads as the whole test and is exactly how the membership-only rule got imported here in the first place. ⚠️ **"Can start now" means it could NOT start THEN — never merely that it can start.** The bound is a **change**, never a state: a set whose rows were already `✅ Ready for approval` and unheld when the operator declined them is the **same ask**, and re-posting it on each decline is the timer loop this bound exists to remove. **The declined snapshot therefore carries each row's startability, and `under-target-state.py` is what records it:** `… write` takes one of `--startable` / `--unstartable` / `--unknown` for **every** row in the set and **refuses to write a state that is missing one**, because a snapshot without its bits is the fail-closed state and cannot be told from a decision. Without that bit nothing distinguishes a row that became startable from one that was startable throughout, and the required `--context` has nothing to name. ⚠️ **The comparison is the script's too — run `… compare` with this tick's per-row classification and act on its exit code:** `0` suppresses (it prints `SUPPRESS:` naming the withheld item id), `10` re-posts (it prints `REPOST:` and **which arm fired** — name that in the card's `--context`), and `3` means no snapshot is recorded, so nothing has been declined yet and the branch posts. ⚠️ **`2` is a REFUSAL, and it is never read as `post`** — malformed input, or a state file that is unreadable or not an object; read the state, `… clear` it if it is corrupt, and re-run. **All four codes are enumerated here for that reason:** a caller holding only `0` / `3` / `10` would take the off-contract `2` for "not suppressed" and post on a state it cannot read. **Never hand-roll the set-difference:** the two arms that must not drift are the unknown verdict above and a row that was unstartable in the snapshot and can start now — and the second is the one a row set alone cannot answer, so a hand-rolled comparison gets it backwards by construction. On `OPEN` the existing poll-first rule already forbids the re-post; `NOT_OPERATOR_ANSWERED:` reads as `OPEN`. On `ANSWERED: approve` the rows were approved — clear the state and post nothing. ⚠️ **The bound is set-change, never a tick count** — a count re-asks a declined question on a timer, which is the defect this rule removes. ⚠️ **Suppression withholds the ASK, never the information:** the capacity line (`workers: <live>/<target>`) and the ranked rows still print on a suppressed tick, so suppression cannot be mistaken for a tick that found nothing — the same discipline `at target: no card` carries above. ⚠️ **The suppression policy has ONE home — THIS bullet, in THIS command, and it is branch-scoped by construction.** The `waiting-approval` bullet above carries its own and different guard (poll before you post) and **no subset suppression at all**: the approve-card clause in `agents/manager-drive.md` — cited by its own opening words, *"Exactly ONE approve-card per run"*, and **never by a line number**, per this repo's own measured rule that a `file.md:N` anchor drifts inside a day — reads *"Zero cards and one-card-per-row both fail"*, so a skip history on this branch's batch is never a skip history on that card. ⚠️ **A topic page records what happened on it; it never carries the rule that decides whether a card is posted.** The two sentences this rule implements are kept here as **history, not policy** — the operator's own words, recorded verbatim on the `MDM Bugs` topic page: *"A `skip` is an answer, not a silence — do not re-post this row"* and *"Re-asking is legitimate only where the set has genuinely changed — a row that has since been repaired to a different state, or a row that was not in that batch — and the tick must say which."* They are cited for the reasoning behind the rule above, **never as its authority** — and never let a per-topic page written by a model become standing fleet-wide policy: that is precisely how one wrong tick became four consecutive ticks of silence on the one card this branch exists to post (measured 2026-10-08).
  - **On `ANSWERED:`** — run `vault-cli task approve` per row the answer names, then open each via `/supervisor:open "<row>"`, exactly as the `waiting-approval` bullet above prescribes. ⚠️ **And `resolve` each row's claim through the same skill** (`/supervisor:asked-ledger resolve --row '<the row>'`) — **on `skip` as well as `approve`**, because the claims are taken at the bullet above *before* the post is decided, so a suppressed tick is holding them too. An unresolved row claim keeps refusing every other manager (exit 3) for the whole prune window, and a row claim has no liveness signal that could shorten it. `NOT_OPERATOR_ANSWERED:` reads as `OPEN`; the gate is not released.
  - ⚠️ **The card is an ASK, not an act.** Nothing is approved and nothing is opened until the operator answers — the same boundary `commands/open.md` § Step 1.5 draws for `phase: todo` rows.
